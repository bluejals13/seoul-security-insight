좋아. 지금 상태라면 다음 작업부터는 “일단 기능을 만드는 것”보다 데이터 계층과 분석 가능성을 먼저 고정하는 방향이 좋아.

특히 지금까지 확인한 걸 보면, Codex와 Antigravity가 서로 다른 방식으로 데이터를 가공해버리지 않도록 작업 원칙을 문서로 남겨두는 것이 중요해.

앞으로의 개발 방향
1. 데이터는 3계층으로 고정
data/
├── raw/          # 원본. 절대 수정/삭제하지 않음
├── processed/    # 서비스/대시보드용 집계 데이터
└── analysis/     # 상세 공간분석·추가 분석 결과


역할은 명확하게:

RAW
 ↓
정제/검증
 ↓
PROCESSED
 ↓
서비스/시각화


그리고 필요할 때:

RAW
 ↓
상세 공간분석
 ↓
ANALYSIS
 ↓
심층 분석/연구


Processed를 다시 Raw처럼 사용해서 상세 분석을 하는 것은 금지하는 게 좋아.

2. Codex와 Antigravity에게 가장 먼저 시킬 일

새 기능부터 만들라고 하지 말고 현재 데이터 파이프라인을 먼저 점검하게 해.

예를 들어 다음 작업을 먼저 시켜.

현재 프로젝트의 raw, processed, utils 구조를 분석하고, 각 데이터가 어떤 원본에서 생성되었는지 추적할 수 있도록 데이터 파이프라인을 정리해라. 원본 데이터는 변경하지 말고, processed 데이터에는 원본 파일과 처리 방법을 명확히 기록할 수 있도록 하라.

그리고 다음을 확인하게 해.

raw 파일
  ↓
어떤 loader?
  ↓
어떤 validation?
  ↓
어떤 transformation?
  ↓
어떤 processed 파일?


이 관계가 코드상 명확해야 해.

3. 특히 가로등 데이터는 지금 방식을 유지

가로등은 중요한 사례야.

현재:

raw
서울시_가로등_위치_2023.csv
        │
        │ 좌표
        ▼
공간 결합
        │
        ▼
processed
서울시_가로등_자치구별_2023.csv


이렇게 하는 건 괜찮아.

다만 processed에는 가능하면 데이터 품질 정보도 함께 관리하는 게 좋아.

예를 들어 별도의 metadata/audit 파일:

processed/
├── 서울시_가로등_자치구별_2023.csv
└── 서울시_가로등_자치구별_2023.audit.json


audit에는:

{
  "source": "서울시_가로등_위치_2023.csv",
  "source_count": 19316,
  "valid_coordinate_count": 19291,
  "assigned_count": 19291,
  "invalid_coordinate_count": 25,
  "processing": "district spatial join + nearest boundary assignment",
  "year": 2023
}


같은 정보를 남기는 식이야.

그러면 나중에 누가

"왜 19,316개가 아니라 19,291개야?"

라고 물어도 바로 설명할 수 있어.

4. 0을 특히 조심

이번 강북구 사례처럼 0이라는 숫자가 실제 0인지, 데이터상 0인지 구분해야 해.

그래서 앞으로 집계 데이터에서 가능하면:

자치구 | 가로등_개수 | 데이터_상태
강북구 | 0 | 확인필요


같은 식으로 품질 상태를 관리하거나 최소한 문서에서 명시하면 좋아.

다만 이걸 모든 화면에 복잡하게 보여줄 필요는 없어.

백엔드/데이터 계층에서는 관리하고, UI에서는 필요한 경우만 표시하면 돼.

5. 범죄 데이터도 같은 방식으로

현재 Raw:

raw/
└── 5대_범죄_발생현황_2024.csv


이건 그대로 둔다.

그리고 서비스용으로:

processed/
└── 5대_범죄_자치구별_2024.csv


예:

자치구,총_발생,살인_발생,강도_발생,성범죄_발생,절도_발생,폭력_발생
종로구,2765,2,5,209,1183,1366
중구,2955,5,5,177,1398,1370
...


이렇게 만들면 대시보드에서는 굉장히 편해.

하지만 Raw에는 검거 데이터까지 있으므로 검거율 등의 추가 분석을 하고 싶을 때 Raw에서 다시 계산할 수 있어야 해.

6. 다음 단계에서 중요한 것은 "분석 모델"

데이터 정리가 끝나면 그 다음부터는 단순 통계가 아니라 치안 분석 로직으로 넘어가야 해.

예를 들면:

범죄 발생
   +
가로등
   +
인구
   +
CCTV
   +
유동인구
   +
상권
   ↓
치안 취약도


같은 구조.

여기서도 원본 데이터를 한꺼번에 하나의 CSV로 뭉개지 않는 것을 추천해.

각 데이터의 원본과 처리 결과를 유지하고, 마지막 단계에서 분석용 feature를 만드는 게 좋아.

7. Codex와 Antigravity의 역할도 나누자

내가 추천하는 방식은 이거야.

Codex

데이터/백엔드/검증 담당

loader
validation
transformation
spatial join
analysis
tests


특히:

데이터 스키마
예외 처리
좌표 검증
공간 결합
재현 가능한 처리
테스트

를 담당.

Antigravity

서비스/UI/사용자 경험 담당

dashboard
map
charts
filter
district selection
risk visualization


그리고 Codex가 만든 분석 결과를 가져와서 보여주는 역할.

즉,

              ┌── Codex ── 데이터/분석
RAW ──────────┤
              └── Processed/Analysis
                       │
                       ▼
                  Antigravity
                       │
                       ▼
                    UI/Map


이렇게 경계를 잡는 게 좋아.

8. 둘이 절대로 임의로 바꾸지 말아야 할 것

다음은 프로젝트 규칙으로 만들어놓는 걸 추천해.

데이터 규칙
raw/ 파일 수정 금지
Raw를 삭제하고 가공본으로 대체 금지
Processed 데이터는 Raw에서 재생성 가능해야 함
좌표 데이터는 가능하면 원본 좌표 유지
집계하면서 정보 손실이 발생하면 Raw를 보존
데이터가 없다고 실제 현황이 0이라고 단정하지 않음
공간 결합에서 실패한 데이터의 수를 기록
처리 결과에는 source와 처리 방법을 추적할 수 있어야 함
9. 그리고 README 또는 DATA_PIPELINE.md를 하나 만들자

이게 상당히 중요해.

예:

docs/
└── DATA_PIPELINE.md


내용:

# Data Pipeline

## 원칙

raw 데이터는 변경하지 않는다.

## 데이터 계층

raw
- 원본 데이터

processed
- 서비스 및 시각화용 정제/집계 데이터

analysis
- 상세 분석용 데이터

## 가로등

원본:
data/raw/서울시_가로등_위치_2023.csv

처리:
1. 좌표 검증
2. WGS84 변환
3. 자치구 경계 공간 결합
4. 미배정 좌표 처리
5. 자치구별 집계

결과:
data/processed/서울시_가로등_자치구별_2023.csv

주의:
자치구별 집계 데이터는 개별 가로등 좌표를 포함하지 않는다.
상세 공간 분석이 필요한 경우 raw 데이터를 사용한다.


이 문서가 있으면 Codex가 작업하든 Antigravity가 작업하든 프로젝트의 데이터 철학이 유지돼.

10. 최종적으로 목표로 할 구조

나는 이 프로젝트를 이런 형태로 가져가는 걸 추천해.

                  ┌───────────────┐
                  │      RAW      │
                  │ 원본 데이터    │
                  └───────┬───────┘
                          │
                    검증 / 정제
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
      ┌──────────────┐         ┌──────────────┐
      │  PROCESSED   │         │   ANALYSIS   │
      │ 발표/서비스용 │         │ 상세 분석용   │
      └──────┬───────┘         └──────┬───────┘
             │                         │
             └──────────┬──────────────┘
                        ▼
                  ┌────────────┐
                  │ Dashboard  │
                  │ Map / Chart│
                  └────────────┘


사용자는 간단하게 볼 수 있고, 분석자는 깊게 들어갈 수 있는 구조야.

그래서 다음 작업 순서

나는 딱 이 순서를 추천해.

① 데이터 파이프라인 정리
↓
② Raw → Processed 재현 가능하게 만들기
↓
③ 데이터 품질/audit 체계 만들기
↓
④ 범죄·가로등·CCTV 등 데이터별 처리 규칙 확정
↓
⑤ 자치구 단위 대시보드 완성
↓
⑥ 상세 공간분석 기능 추가
↓
⑦ 치안 취약도/위험도 분석 모델 개발
↓
⑧ UI에서 "간단 보기 ↔ 상세 분석"을 선택할 수 있게 만들기

이렇게 가면 지금처럼 "발표하기 편한 데이터"와 "실제로 깊게 분석할 수 있는 데이터" 사이에서 나중에 다시 뜯어고치는 상황을 크게 줄일 수 있어.

그리고 다음에 Codex에게 작업을 넘길 때는 내가 지금까지 확인한 내용을 바탕으로 바로 붙여넣을 수 있는 Codex 작업지시서 형태로 만들어서 주는 게 가장 좋다. Antigravity용도 별도로 만들고, 둘이 건드리는 영역도 명확하게 나누는 게 좋고.
